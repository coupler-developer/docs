## 릴리스 결과

- DB migration: 개발계는 모든 writer와 effect producer를 fence하고 TLS, identity, drain, logical backup,
  exclusive lock과 live postcondition을 확인한 뒤 migration 91 ledger-only recovery를 완료했다. 다음 runtime
  `908ebc0`으로 FENCED smoke, RESUMED, service-completed까지 기록했다. 운영계는 canonical 도입 전 실행을
  사후 제조하지 않고 live catalog 23/23 resolved, pending·adjudicable gap 0건과 migration 91
  postcondition을 다시 확인한 일회성 처분으로 scope를 닫았다.
- contracts package: `@coupler-developer/coupler-api-contracts@0.1.22` 발행과 Admin·Mobile
  manifest/lockfile exact pin을 확인했다. 발행 workflow source `1a2a6c9`, Production API tag source
  `8aa8583`, 이후 main `908ebc0`의 `packages/contracts` tree가 모두 같음을 확인해 scope를 닫았다.
- API: 운영 배포 source `8aa8583`과 외부 기본 응답을 확인하고 해당 커밋에 `v2.3.0`을 고정했다.
  이후 maintenance executor 변경만 담은 `908ebc0`이 main에 병합됐지만 annotated tag를 불변 릴리스
  기준으로 유지한다. tagged source의 전체 contract/core/worker 검증과 운영 runtime/queue inventory로
  forward-fix 복구 증빙은 고정했다. 다만 직전 소비자의 legacy route 차단과 이전 native bootstrap
  envelope 불일치는 배포 뒤 확인됐다. 과거 사전 증빙을 만들지 않고 `violated` 처분으로 종결했다.
- Admin: current source의 정적 build와 운영 산출물 일치, 외부 응답과 품질 게이트를 확인하고
  `v2.3.0`을 고정했다.
- Mobile Store: Android·iOS 2.3.0 (101) 출시와 기본 smoke, `v2.3.0` 태그를 확인했다. 공통 제출
  마커 증빙을 원격 릴리스 기록 PR에 이관한 뒤 로컬·원격 마커를 삭제했다.

## 롤백 기준

- DB: `RESUMED` 뒤 snapshot/PITR로 되돌리지 않는다. 현재 runtime과 데이터 보존을 전제로 forward fix 또는
  통제된 lossless reconciliation을 사용한다.
- API: 직전 운영 기준점과 직전 client는 현재 DB·계약에서 전체 복구 조합이 아니므로 rollback하지 않는다.
  durable FCM outbox가 없는 상태에서 현재 DB를 보존하고 forward fix 또는 대상이 식별되는 통제된
  reconciliation만 사용한다.
- Admin: 배포 직전 정적 산출물은 제거된 legacy concierge route를 호출하므로 current API에서 복원하지
  않는다. current artifact를 유지하고 API·Admin forward fix 뒤 nginx 내부·외부 응답을 재확인한다.
- Mobile Store: Android·iOS가 이미 출시됐으므로 새 Store build 또는 NextPush rollback을 별도 판정한다.
- Mobile NextPush: 직전 label은 제거된 legacy chat route를 호출하므로 current API에서 rollback하지
  않는다. 양 플랫폼 current label을 유지하고 client/API forward fix를 별도 판정한다.
- docs: 최종 PR 병합 뒤 `v2.3.0` 태그와 Release를 생성하고 실패 시 별도 운영 이슈로 추적한다.

## 후속 작업

- 이번 릴리스에 남은 배포 범위는 없다. 확인된 API 호환성 위반은 향후 릴리스의 정상 Gate 증빙으로 재사용하지
  않으며, 다음 계약 변경부터 배포 전에 소비자 호환 또는 결정론적 차단을 검증한다.
- 그룹미팅의 배포·현행 논리 모델 판정과 분리된 FCM·실시간·scheduler 운영 smoke 증빙은
  [기술 부채 인벤토리](../technical-debt/technical-debt.md)의
  `그룹미팅 FCM·실시간·scheduler 운영 smoke 증빙 미확인`에서 비차단 후속 검증으로 추적한다.
